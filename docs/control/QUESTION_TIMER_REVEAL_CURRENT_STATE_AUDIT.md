# Question Timer and Answer Reveal Current State Audit

## 1) Executive summary

Current question rounds are functional but not designed for the rehearsal feedback flow:

- Master opens the next question.
- Runtime question and player assignments are created immediately.
- Player screens receive answer options immediately.
- TV starts a visual client-side timer when it first renders the active question.
- Correct answer is not intentionally displayed in normal active view, but it is already present inside state/content payloads used by frontend code.
- TV reveal can happen when the question is closed by backend or when the local TV timer reaches zero.

Recommendation: **phased reveal patch** is needed before tuning timer length. Copy-only or timer-only tuning will not solve the core concern that options and answer data are already available too early.

## 2) Current question round flow

Question flow is implemented through host round runtime:

- `app/routes/dev.py`
  - `POST /dev/host-rounds/start-series/{room_code}/{round_code}`
  - `POST /dev/host-rounds/{host_round_id}/open-next-question`
  - `POST /dev/host-rounds/{host_round_id}/force-close-question`
  - `GET /dev/host-rounds/{host_round_id}/debug`
- `app/services/host_round_service.py`
  - `open_next_question_for_host_round`
  - `force_close_current_question_by_host`
- `app/services/assignment_service.py`
  - answer evaluation and automatic closing when all assignments are answered.

Opening a question creates `GameHostRoundQuestion(status="active", answers_open=True)` and issues `GameAssignment` rows to eligible players immediately.

## 3) Player view behavior

Player question UI is in `app/templates/player_room.html`.

The polling endpoint is:

- `GET /player/me/{player_token}/assignments`

The player receives issued assignments and renders:

- title/prompt,
- answer options or statements,
- text input for free text questions,
- confirmation button for confirm-style tasks.

Answer options are shown immediately when the assignment is issued. There is no separate “question only” state for players.

## 4) TV view behavior

TV question rendering is in `app/templates/tv_mode_tv_state.html`.

TV uses:

- active host round from `tv-state`,
- debug data from `/dev/host-rounds/{host_round_id}/debug`,
- runtime question content,
- local JS state for question focus, timer, and reveal mode.

When no question is active, TV shows a waiting state: the question appears after Master opens it.

When a question is active, TV renders prompt and options together through `renderQuestionPromptMarkup`.

## 5) Master view behavior

Master controls are in `app/templates/master_screen.html`.

Current Master action flow:

- if no active question: show action `Открыть вопрос`;
- if question is active: show action `Закрыть вопрос`;
- if round is completed and waiting: show action `Завершить раунд`.

Master currently has no separate action for:

- show question without options,
- show options,
- start timer,
- reveal answer.

## 6) Timer implementation

Timer is mainly frontend-driven on TV:

- `questionTimerDurationSec` is derived from `current_question.time_limit_sec`, `timer`, or `duration_sec`.
- fallback is `45`.
- `questionTimerEndsAt = Date.now() + questionTimerDurationSec * 1000`.

This means the TV timer starts when the active question is rendered on that TV client, not from a shared backend timestamp.

Player screens do not have the same visible shared countdown in the inspected flow. Their ability to answer is controlled by assignment status and runtime question `answers_open`.

## 7) Answer option reveal behavior

Options are visible immediately:

- on TV through question content options/statements,
- on player room through assignment content options/statements.

There is no current backend or frontend stage that supports:

- question visible first,
- options hidden,
- options opened later by Master.

## 8) Correct answer reveal behavior

TV reveal behavior is controlled by `isQuestionRevealMode`:

- reveal when local TV timer ended,
- or when `answers_open === false`,
- or when runtime question status is no longer `active`.

Correct answer display is generated by `renderQuestionReveal`.

Important risk: correct answer exists in question content payload (`correct_answer`) before reveal. It is not normally rendered in active mode, but it is available to frontend/browser code and debug/state consumers.

Player answer result payload also can include `correct_answer` after answer processing.

## 9) Anti-google weakness assessment

Current anti-google weakness is high:

- players see options immediately;
- timer may be long enough to search;
- TV timer is not a strict shared backend clock;
- if host must read question aloud, players can already see options and start searching;
- correct answer data exists in payload before intended reveal, even if not displayed.

The most important fix is not just shorter time. The system needs staged visibility.

## 10) Suspected early-answer reveal check

No evidence was found that active TV view intentionally displays the correct answer before reveal.

However, answer data is present early in payloads:

- `current_question.content.correct_answer`,
- assignment template content,
- debug payloads.

So the suspicion is partly valid from a data-exposure perspective: the correct answer is available too early to browser/debug clients, even if normal UI does not print it until reveal mode.

## 11) Feasibility of phased reveal

Feasible with a minimal V1 patch, but it needs runtime state or explicit derived state.

Desired stages:

1. Question-only stage
   - Master opens question text to TV.
   - Player answer assignments are not yet answerable or options are hidden.

2. Options stage
   - Master opens answer options.
   - Player options become visible.

3. Timer stage
   - Timer starts from a backend timestamp or explicit Master action.
   - TV and player clients derive the same countdown.

4. Answer reveal stage
   - Master closes question/reveals answer.
   - Correct answer appears only after this point.

Smallest practical implementation likely needs fields or metadata for `visibility_stage` and `timer_started_at`. Without schema changes, it could be stored in existing runtime question metadata if such a JSON field exists; otherwise it becomes a small schema/runtime patch.

## 12) Risks of changing current flow

- Host-round assignments and answer processing assume `answers_open=True` at question open.
- Player room currently renders options from assignment content immediately.
- TV currently treats active question as ready-to-show.
- Removing `correct_answer` from payloads must not break auto-checking, reveal view, or debug screens.
- Timer synchronization needs careful handling so refreshes do not restart the timer.

## 13) Recommendation

Recommended decision: **phased reveal patch**.

Do not start with timer tuning alone. A shorter timer may feel unfair while players must read question/options themselves, and it does not solve early option visibility.

Do not start with a larger redesign. Existing host-round infrastructure can probably support a V1 staged flow if scoped tightly.

## 14) Minimal proposed next task

Implement Question Reveal V1:

- add a runtime question visibility stage or equivalent metadata;
- Master actions:
  - show question,
  - show options and start timer,
  - close/reveal answer;
- TV:
  - question-only card before options,
  - options only after stage changes,
  - answer only after close/reveal;
- Player:
  - no answer options until options stage;
  - clear waiting text while host reads question;
- sanitize frontend/debug payloads so `correct_answer` is not sent to player/TV active mode before reveal.

Keep scenario JSON, question bank, and balance unchanged unless a later implementation task explicitly approves otherwise.
